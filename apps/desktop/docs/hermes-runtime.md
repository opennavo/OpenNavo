# Hermes runtime integration

OpenNavo ships a pinned Hermes Agent runtime as an optional sidecar. The app does
not bundle the ~330 MB runtime; the assistant asks before installing it.

## Current pin

The single source of truth is `apps/desktop/hermes/runtime.json`. It pins all
inputs and the published archive together:

| Component             | Value                                                            |
| --------------------- | ---------------------------------------------------------------- |
| Hermes Agent          | `0.23.1` (`v0.23.1`, `3b421578588243f920886e6fe79a6faa87ea026e`) |
| Python                | `3.14`                                                           |
| CuaDriver             | `0.26.1`                                                         |
| github-copilot plugin | `4987918a068fcf4b3efbb584db5dd05e5f57c669`                       |
| Runtime release       | `hermes-runtime-v0.23.1`                                         |
| Package               | `runtime-0.23.1-macos-arm64.tar.gz`                              |

Both build scripts read this file. The Rust app compiles the same file into the
binary, so the expected version and default release URL cannot drift from the
package that was built.

## Build and package

The runtime is generated, not committed:

```bash
pnpm --filter @opennavo/desktop hermes:prepare -- --force
pnpm --filter @opennavo/desktop hermes:package
```

`hermes:prepare` builds standalone CPython, Hermes from the pinned tag, the
pinned CuaDriver, and every plugin pin under
`apps/desktop/src-tauri/resources/hermes`.

Before reporting success it runs all of these checks:

- `site/install-stamp.json` is generated by upstream
  `scripts/write_install_stamp.py` with `payload: runtime`,
  `distribution: desktop-app`, and `updateMechanism: external`.
- `hermes --version` is run with a temporary, empty `HERMES_HOME` and must
  report exactly the version in `runtime.json`. A host `~/.hermes` checkout
  cannot satisfy this check.
- `CuaDriver.app` exists, has its executable, and matches the pinned version.
- Every pinned plugin exists and its `.hermes-catalog.json` SHA matches.
- No `build-home` directory is left in the artifact.

`hermes:package` repeats those checks, creates the archive, writes its SHA-256
next to it under `apps/desktop/hermes-dist/`, and updates
`release.sha256` in `runtime.json`. Commit that manifest change with the
runtime release work.

Development can install from a prepared directory with
`HERMES_RUNTIME_SOURCE=/path/to/resources/hermes`. Installed desktop builds
download the archive from `release.repository`, `release.tag`, and
`release.asset`, then verify the pinned SHA-256 before extraction.

## Upgrading an existing user

Users on `Hermes 0.23.0` keep their runtime until they explicitly update it:

1. Ship a new OpenNavo desktop version containing this runtime manifest.
2. The app reads the installed runtime with an empty `HERMES_HOME`. An
   unstamped `0.23.0` package therefore reports no identity and is marked
   `outdated`; it no longer borrows the version from `~/.hermes`.
3. The Hermes settings pane and the assistant rail show the pinned target and
   an **Update runtime** button. Nothing is replaced in the background.
4. The installer downloads to `runtime.tmp`, verifies SHA-256, verifies that
   the staged runtime reports `0.23.1`, then swaps `runtime/hermes`.
5. Pinned plugin copies already owned by OpenNavo are staged from the new
   runtime and swapped in the same operation. A copy is considered managed
   only when its `.hermes-catalog.json` names the same `catalog_name` and
   repository as the pin. A plugin the user installed from another repository
   is left untouched.
6. If activation, version verification or plugin activation fails, the
   previous runtime and plugin copies are restored automatically.

The update replaces `OpenNavoData/runtime/hermes` and refreshes only the
OpenNavo-managed plugin copies. The following stay in place:

- `OpenNavoData/hermes/` — `HERMES_HOME`, `config.yaml`, `.env`, `auth.json`,
  sessions, memory, logs, audit, user-managed plugins and caches.
- `OpenNavoData` panel sessions.
- CuaDriver's macOS TCC grants, because the app is outside the signed bundle
  and keeps its identity.

Hermes 0.23.1 raises the config schema from 52 to 53. The only explicit
migration changes the default `agent.clarify_timeout` from `3600` to `90`;
an explicitly configured value is preserved. Hermes performs that migration on
first launch with the new runtime. OpenNavo's config writes are merge-based and
do not reset `_config_version` or keys the desktop does not own.

Publishing a new runtime release alone does not upgrade users still running an
older desktop build. Their installed app has the old hard-coded default. The
desktop app release must ship before they can see and use the new runtime.

## Following a new Hermes release

Check upstream and move the pin:

```bash
pnpm --filter @opennavo/desktop hermes:check
pnpm --filter @opennavo/desktop hermes:bump -- --version 0.24.0
```

`hermes:check` reads the latest stable Hermes GitHub release. `hermes:bump`
fetches the stable tag and immutable commit, updates the Hermes version, tag,
commit, commit timestamp, runtime release tag and asset name, and clears the
old checksum. It refuses drafts, prereleases, mutable refs, and non-SemVer tags.

Review the diff, then update any changed sidecar pins explicitly:

```bash
pnpm --filter @opennavo/desktop hermes:bump -- \
  --version 0.24.0 \
  --cua-version 0.27.0 \
  --plugin-ref <40-char-sha> \
  --python 3.14
```

Do not use a canary tag or a moving branch for production.

Then run the release sequence:

1. `hermes:prepare -- --force`
2. `hermes:package`
3. Run a gateway smoke test with an isolated `HERMES_HOME`: install, start
   `hermes serve --skip-build`, check `/api/status`, create a session over
   `/api/ws`, and confirm the Python, CuaDriver and plugin versions.
4. Publish `hermes-runtime-vX.Y.Z` with the tarball and `.sha256`. GitHub
   Release copy must be English only.
5. Build the desktop release that contains the updated `runtime.json`.
6. On macOS, sign, notarize, `stapler staple`, `stapler validate`, then rebuild
   and verify the updater archives/DMG from the stapled app.
7. Add desktop release notes for all 10 client locales.
8. Test both a clean install and an in-place `0.23.x` runtime update before
   enabling the production update route.

The runtime GitHub release must exist before the desktop release is published:
the app's compiled default URL points at it.

## Rollback

An update that fails SHA, extraction or version verification never replaces the
working runtime. If final runtime or plugin activation fails, the previous
runtime and plugin copies are restored before the command returns.

Keep the previous runtime GitHub release and tarball available. If a shipped
runtime has a runtime-level regression, move the manifest back to the previous
version and SHA, rebuild the desktop app, and ship that pin. Do not advise users
to delete `OpenNavoData`; that would remove sessions and credentials.

## Data root

All Hermes runtime and state live under:

```text
~/Library/Application Support/com.opennavo.desktop/OpenNavoData/
```

- `runtime/hermes/` — optional runtime
- `hermes/` — `HERMES_HOME`, sessions, memory, logs, audit

Provider API keys live in `hermes/.env` (`HERMES_HOME/.env`), as `KEY=value`
lines in a `0600` file. The app does not maintain a second credential store.
WebKit's own WebsiteData remains under
`~/Library/WebKit/com.opennavo.desktop/`.

## Runtime contract

- `hermes_runtime_status` reports whether the runtime is installed, the
  runtime-reported version, the pinned expected version, the single
  `OpenNavoData` path, and whether the computer-use driver is present.
- `hermes_runtime_install` downloads/copies the runtime into
  `OpenNavoData/runtime/hermes`, emits `hermes-install-progress`, verifies the
  SHA-256, verifies the staged and activated versions, refreshes stale
  OpenNavo-managed plugin copies, and restores the previous runtime and
  plugins on failure. `hermes_runtime_uninstall` removes the entire
  `OpenNavoData` root and deletes stored keys and panel sessions with it;
  CuaDriver and macOS TCC grants are left alone.
- `hermes_chat` starts a local `hermes serve` gateway and streams
  `message.delta` frames from `/api/ws` as `hermes-chunk` Tauri events. The
  final `message.complete` frame becomes the persisted assistant message.
- The desktop uses the gateway only. CLI fallback is intentionally disabled so
  steering, approvals and tool events always share one transport contract.
- Full control enables the session-scoped gateway YOLO flag; guarded and
  safe modes do not, and approvals are denied unless the user grants them. The
  gateway toolsets are selected with `HERMES_TUI_TOOLSETS`.
- `hermes_stop` interrupts the active child and stops the gateway.
- Provider keys live in `HERMES_HOME/.env`; a key supplied with a turn is
  written there and the runtime reads it itself. `HERMES_HOME/auth.json`
  belongs to Hermes and is never read, rewritten or scrubbed by the app.
- Each conversation stores the gateway's `stored_session_id` and resumes it
  with `session.resume`, so follow-up turns keep agent context.

## Mac control and TCC

`terminal` and `file` work through Hermes. `computer_use` additionally needs
the optional runtime's `CuaDriver.app`, which must be granted:

- Accessibility
- Screen Recording
- Full Disk Access only for tools that read those locations

TCC cannot be granted programmatically. The settings UI labels these
permissions as first-use/on-demand and opens System Settings; validate on a
signed build and a clean Mac. The runtime package contains `CuaDriver.app`
(signed by Cua AI, Inc.); TCC grants name CuaDriver.

## Known gaps

- The gateway streams token deltas and tool/reasoning events.
- Skills/tools/cron are viewable and have basic management; MCP server config
  editing is not exposed.
- The model catalog is official metadata when available, with a clearly-marked
  static fallback.
- Computer-use TCC validation and notarization are release-environment work.
- Hermes's own session store is used for continuity; OpenNavo keeps the visible
  transcript for history and search.
